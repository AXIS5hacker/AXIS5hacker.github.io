OMP（oh-my-pi）是终端里的编码 agent，@kahme247/ompweb 给它套了一层浏览器界面。把两者装进同一个镜像、用 Docker Compose 起一个容器，就能得到一个”浏览器里聊天、宿主机上留文件”的自托管开发环境。下面是从零到跑通的完整过程。

前置条件

  • Docker Engine 或 Docker Desktop（自带 Compose v2，命令为 docker compose）
  • 一个放配置和代码的目录，本文以 D:/ohmypi 为例
  • 需要联网：镜像里会在构建时拉取 npm 包

目录结构

omp_config 和 workspace 都先建空目录即可，容器会往里面写。

Dockerfile：一个镜像装 OMP 和 ompweb

OMP 是 Bun 运行时下的 CLI，ompweb 是 Node 应用（要求 Node >= 22.19）。以 node:22-bookworm 为基础镜像，再把官方 oven/bun 镜像里的 bun 二进制拷进来，一个镜像里两套运行时都有了。

两个包的运行方式不同，别搞混：omp 是挂在 /opt/bun/bin/omp 的 Bun 可执行文件，ompweb 是 Node 的 npm 全局命令。所以下面要把 OMP_WEB_OMP_BIN 明确指到前者。

.dockerignore

构建上下文里只需要 Dockerfile，把工作区和密钥全部排除，既快又不会把敏感文件送进镜像层：

.env

密钥单独放，不要写进 docker-compose.yml：

docker compose 会自动读取 compose 文件同目录下的 .env 做变量插值；而 env_file: 是把变量真正注入容器。两者不是一回事，这里两个都需要。

docker-compose.yml

几个关键点：

  • PI_CODING_AGENT_DIR 用下划线，且必须与挂载点一致（/omp_config）。配置、会话数据库都在这个目录下。
  • OMP_WEB_HOSTNAME=0.0.0.0 只是让服务在容器网络里监听所有接口；真正决定对外可见性的是 ports: 那一行。所以监听 0.0.0.0 + 只发布到 127.0.0.1 是安全组合，再加上 OMP_WEB_PASSWORD 做一层认证。
  • stdin_open / tty 是为了以后用 docker compose run --rm omp 进交互式 CLI 时不会立刻退出。
  • image: ohmypi-local:latest 是本地构建的镜像名，docker compose pull 拉不到它。

构建与启动

浏览器打开 http://127.0.0.1:30177，用 OMP_WEB_PASSWORD 登录（登录用户名固定为 omp）。首屏会由 ompweb 通过 stdio 起一个 omp --mode rpc-ui --cwd <cwd> 子进程来承载会话，所以不要把 ompweb 理解成”接管某个终端进程”。

启动后的两件事

进入界面后按顺序做完这两步，后续新建会话才会落在你想要的地方：

  1. 工作区：侧边栏 Add project，填容器内路径，例如 /workspace（对应宿主机 D:/ohmypi/workspace）。项目列表的第一行就是新会话的默认工作区，也是资源管理器的根。填宿主机路径会报 directory_not_found——路径是在容器里校验的。
  2. 默认模型：设置 → API 密钥与提供商 → 「OMP 模型角色」→ 给 default 角色选好模型并保存。这一项写的是 OMP 自己的 config.yml 里的 modelRoles.default，新会话的模型按钮初值就取自它；在会话里临时切换模型不会写回配置。

接入自定义模型提供商：models.yml 与 config.yml

两个文件分工不同，别写反：

  • models.yml：定义提供商和它们的模型（端点、鉴权、模型元数据）
  • config.yml：决定哪个角色用哪个模型（modelRoles、retry.fallbackChains）

两者都在 agent 目录下，按本文的挂载就是容器内 /omp_config/models.yml 与 /omp_config/config.yml（宿主机 D:/ohmypi/omp_config/）。OMP 内置了 deepseek、xiaomi 等提供商，能直接用就不用自建；自部署网关、中转站、公司内网端点才需要手写。

models.yml：定义一个自定义提供商

  • 根节点**只允许有 providers**。多写一个键（比如 setupVersion）会让整个文件过不了 schema 校验，结果是自定义提供商被静默跳过——表现成”配置明明写了却没这个模型”。
  • apiKey 的取值规则是环境变量名或字面量：这个字符串若正好是已存在的环境变量名，就用它的值；否则字符串本身被当密钥。所以这里写 CUSTOM_API_KEY，不要写 ${CUSTOM_API_KEY}，也不要写明文密钥（密钥放 .env 里注入）。以 ! 开头的值会被当 shell 命令执行并取 stdout。
  • 在鉴权优先级里，models.yml 的 apiKey 排在存储的 OAuth 之前，这正是给自定义 baseUrl 配的密钥不会被上游 token 覆盖的原因。
  • 不需要鉴权的本地端点用 auth: none 顶替 apiKey，例如 ollama / llama.cpp / LM Studio。
  • api 取 openai-completions（Chat Completions 风格）或 openai-responses（Responses 端点）。

不依赖自动发现时，手工列出模型：

带自定义 models 的提供商必须给 baseUrl、api（提供商级或每个模型上都有），以及 apiKey 或 auth: none。模型条目还能写 cost（input/output/cacheRead/cacheWrite）、maxContextWindow、headers、compat 等。

用自动发现就不必逐条列模型：

discovery 需要提供商级 api（type: proxy 除外），type 可选值是 ollama、llama.cpp、lm-studio、openai-models-list、proxy、litellm。默认会往 baseUrl 后拼 /v1，遇到 https://api.example.com/v3/compat 这类网关要设 injectV1: false，否则请求到的是另一份更小的模型列表。发现出来的容量元数据不一定准确，用 modelOverrides 覆盖：

只给内置提供商改个别模型的元数据时，不用写 models——只写 modelOverrides（或 baseUrl、headers、compat、discovery 之类）也是合法配置。

config.yml：把角色指向自定义模型

  • 选择器格式是 provider/modelId，也就是 models.yml 里的提供商 id 加上模型 id。
  • chat 类角色可带思考等级后缀：:minimal、:low、:medium、:high、:xhigh、:max；image、web、speech、dictation、judge 这类 model-kind 角色不带。
  • 角色值写成 @别名 时必须在 YAML 里加引号，例如 plan: "@slow"。
  • default 是会话主模型，也就是 Web UI 新建会话时模型按钮的初值；smol 服务轻量任务，slow 做深入分析，tiny 生成会话标题，vision 处理图片，advisor 是顾问模型。
  • retry.fallbackChains.<role> 是同一角色的兜底顺序；写 [] 表示明确不兜底。
  • 角色映射属于 config.yml，不要塞进 models.yml（后者只认 providers）。改 default 角色时，若会话里改过模型而没写角色，那只是会话级选择，不会持久化。

让改动生效与排查

配置文件都在挂载目录里，改完不用重建镜像：

  • 改了 models.yml：Web UI 按文件 mtime 检测到变化并重建模型列表，刷新页面即可看到新提供商；但已经在跑的 omp 子进程只在启动时读一次，下一个新会话才用上新配置。
  • 改了 config.yml 的 modelRoles：同样是”下一个新会话生效”，进行中的会话保持它启动时的模型。
  • 只是加一个密钥环境变量：改 .env 后 docker compose up -d omp 重建容器，不需要重新构建镜像。
  • 自定义文件没加载，先怀疑 YAML 与 schema：omp models 就能验证；根节点只允许 providers。

升级与运维注意

  • 镜像里装的是 @latest 的两个包。要真正更新，必须绕过旧的安装层：

  • 升级前先备份 omp_config/。配置与会话数据库可能带迁移，旧镜像回滚并不能撤销已经迁移过的状态。

  • 不要把 30177 直接发布到 0.0.0.0 或公网。要远程访问就走 VPN，或者用反代补上 TLS，并保留密码认证；明文 HTTP 暴露这个界面等于把宿主机上 agent 的写权限交出去。

  • docker compose exec omp omp 与浏览器里的会话是各自独立的进程，同时改同一批文件容易互相覆盖，别两边一起动同一个仓库。

小结

整套东西只有一个镜像、一个服务：node:22-bookworm 里装上 Bun 版 OMP 和 Node 版 ompweb，挂两个目录（配置、工作区），把 30177 只发布到回环地址，剩下的交给 Web UI。构建、启动、探活各一条命令，升级时记得 --no-cache 和备份 omp_config/。
